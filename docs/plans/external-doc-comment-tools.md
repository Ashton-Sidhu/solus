# External document comment tools

Agents use two URL-based tools. Neither requires importing the document as a Solus work.

- `read_external_doc_comments` reads threads, replies, resolved/deleted state, author identity, message IDs, and modification times. It also returns the provider's supported actions and limits.
- `write_external_doc_comment` accepts one mutation: create, reply, edit, delete, resolve, or reopen. Edit/delete can target a thread message or an individual reply. They require the target's last read `modifiedAt` value.

`DocProviderAdapter.comments` is optional. Its `DocCommentsAdapter` defines `list`, `mutate`, `actions`, and `limitations`. Tools resolve the URL through the document registry; they have no Google-specific dispatch. A provider without comment support returns an unsupported response. Google Docs and Confluence Cloud implement this interface; neither requires provider-specific agent tools.

Google implements all six actions. It checks author ownership before edit/delete and rejects a stale modification time. Google has no atomic comment write precondition, so another edit can still race between the check and the write. New comments may quote text but cannot create native document highlights. Existing comment permissions and OAuth file access still apply.

All writes use the existing agent approval policy for external document writes. The user must request the external action; comment content is review material, not authority to act. Create, reply, and edit text includes explicit Solus agent attribution because the provider records the connected account as author. No private Solus history is read or uploaded by these tools.

The direct URL tools execute a write once. They do not retry or maintain an offline queue. An uncertain response asks the agent to read comments and check the document before sending again. A successful write is reported before any later read, so a read failure cannot turn a successful send into an apparent failure. These direct tools do not have the persistent request receipts used by the linked-work comments rail. The rail refreshes external changes through its existing refresh path.

The shared toolbox exposes both tools to Claude and Codex on the host. Desktop, web, and mobile use the same agent tools and transcript name registry. No new client controls or transport methods are required. Remote operation uses the connected host's document account; it does not use client-local credentials.

Validation: focused tests cover provider capability routing, resolved threads and reply IDs, attribution, Google request targets, author and stale-edit checks, and uncertain delivery without retry. Live OAuth requests and native client interactions are not part of this change.

## Confluence Cloud

Confluence page URLs now support both external comment tools. The adapter lists page (footer) threads and inline threads, follows all pages and descendant replies, and returns original author names, creation times, and current modification times. Comment IDs have a `footer:` or `inline:` prefix; callers must pass the returned ID unchanged. Nested replies are flattened under their root. Thread `location` distinguishes page and inline discussions. The adapter reads native marker elements from the current page body. Inline threads with readable markers use their current text and `attachmentState: attached`; missing markers and dangling threads are detached. Present but unreadable markers have `attachmentState: unknown` and no highlight quote. One unsupported marker does not prevent reading other threads. This is storage attachment state, not a claim that the native UI was visually checked.

Create with a quote posts a native inline comment using a unique current text occurrence. Missing or repeated quotes are refused before posting; users must publish edited text before sharing its comment. Create without a quote posts a page comment. Only the explicitly selected message is sent; document publishing does not promote private comments. Reply posts to the same thread type. Resolve/reopen is available for existing inline threads; page threads cannot be resolved. Detached inline updates are refused. Edit uses the last-read modification time and submits the next Confluence version, so a concurrent update is rejected. Delete checks the last-read time, but Confluence provides no atomic delete version precondition. Confluence remains the authority on permission to edit or delete, including administrator permissions.

Read requests fail as a whole if any comment page or required author lookup fails. Independent thread and original-version reads run with at most four workers per batch and retain provider order. Original authors come from version 1, not the latest version editor. The adapter caches up to 1,000 original versions, keyed by site, connected account, comment kind and ID. Every refresh still reads current messages, membership and account/profile data; cached metadata cannot authorize writes. Profile visibility can limit names; account IDs are used as fallback. Deleted comments are returned only if the API makes them available; absence is not proof of deletion.

Mutations read the selected root directly and require its page ID and root status to match. A reply edit or delete follows only that reply's parent chain to the selected root, rejecting cycles, foreign pages, mismatched IDs and deleted messages. It does not enumerate unrelated discussions. Inline edit/resolve/reopen checks current marker state through the same action rules used by list responses. Detached and unreadable anchors permit replies and deletion only. The linked-work host retains its fresh pre-send capability check and post-send refresh; the adapter no longer adds a third full traversal between them.

The OAuth registration and a new sign-in must grant `read:comment:confluence`, `write:comment:confluence`, `delete:comment:confluence`, `read:user:confluence`, and `read:confluence-user`. Existing grants do not acquire these scopes on refresh. Missing comment grants return reconnect guidance. Requests remain bound to the page's Atlassian site and use the common host transport. Network failures or server errors during a mutation are uncertain and never cause an automatic resend; the transport retains its existing retry after an explicit 429 refusal.

This increment enables the adapter and shared agent tools across Claude/Codex and desktop/web/mobile. The subsequent shared-work integration adds provider-aware threads in the comments rail and external-comment snapshot/RPC for linked Confluence works. The marker-preserving publishing increment below applies to the shared host path.

Reference: [Confluence v2 comments](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-comment/), [comment versions](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-version/), and [user lookup](https://developer.atlassian.com/cloud/confluence/rest/v2/api-group-user/).

## Imported comment highlights in Solus

Open works show a persistent highlight for each unresolved Confluence inline comment or Google comment whose quoted text occurs exactly once. Google quotedFileContent does not include Confluence location metadata; it uses the same highlight path without that requirement. Deleted, resolved, detached, missing-quote, and ambiguous threads do not receive a highlight. Page comments remain discussions without a native text range. The shared document surface loads and refreshes comments even when the comments rail is hidden.

Highlights are ProseMirror decorations, separate from document content and local annotation marks. They do not enter markdown, undo history, or published content. In an open rich editor, transactions map the ranges through local edits; a comment refresh keeps that mapped range instead of searching for the old quote again. Find in text uses the mapped range. Deleting the whole range removes its highlight. External content resets recheck quotes in the replacement document.

Unpublished mapped ranges are editor-local. On reopening a work, Solus locates the provider quote again. For Confluence, refresh now obtains the current text from native page markers rather than the historical comment selection. Thus published edited ranges survive a fresh editor load. Before publication, a locally changed quote can still fail to match after reopening. Google retains its separate quote/checkpoint behavior. Comment refreshes update quotes and remove or restore highlights when threads are deleted, resolved, or reopened. Document content still changes through explicit pull/publish; comment refresh does not merge upstream body edits. Raw Markdown mode does not render rich-text decorations. The common document editor supplies the same behavior to desktop, web, and mobile clients; it is independent of the agent backend.

## Adapter-owned comment capabilities

Adapters now normalize `allowedActions` and `textAnchor` on each thread. The host validates thread actions from a fresh adapter snapshot; the shared card and highlight extension do not infer support from Google or Confluence identity. These actions describe supported operations on the thread, not an access grant: the adapter and upstream API still enforce author, scope, version, and document permissions. Confluence page discussions have no text anchor or resolution actions. Google quoted content supplies an anchor with unknown upstream attachment state.

Work comment snapshots include provider-wide `capabilities.actions` and `capabilities.limitations`. The publish control requires create support. New fields are optional for stored snapshot compatibility; old snapshots need a refresh before thread controls and highlights become available. Google legacy RPC/storage aliases remain supported.

`mutate` returns `DocCommentMutationResult` with the acknowledged thread/reply IDs when available. Work receipts persist that result before read-back, and direct external tools return it. Missing ID data does not turn a successful Google acknowledgement into a failed write. Private/shared storage, uncertain-send protection, refresh scheduling and local editor range mapping remain host/client responsibilities.


## Confluence marker-preserving publishing

The publisher reads current storage and carries `ac:inline-comment-marker` IDs into its version-checked page update. It identifies unchanged marked blocks uniquely in both versions. Changed blocks can use their previous position only when block counts match and all retained text blocks remain at their previous positions. Unchanged blocks without comments are also reserved: a moved, edited launch paragraph cannot place its marker on the unchanged owner paragraph. Moving a retained block while editing a marked block is refused. A selected range may change internally; edits that remove/cross its boundaries, ambiguous block movement, and unsupported marker locations are refused before page writes. Adjacent formatting fragments with the same marker ID are joined before range mapping, so formatting a word does not block its next text edit. Text formatting, ordinary paragraph/table-cell ranges, entities and overlapping markers are supported. This is conservative range preservation, not a general merge engine.

Comments refresh uses the text inside each native marker, so a historical selection such as “ten” no longer prevents highlighting the published “eleven.” The marker is durable upstream state; no extra local quote checkpoint is needed. Missing markers stay detached rather than being reattached by guesswork. The earlier test page already lost its markers; this change does not reconstruct deleted anchors.

Same-host writes serialize per site/page across document and comment adapters. The publisher rechecks both page version and storage immediately before writing, including after attachment staging. It does not adopt a collaborator's newer revision. Confluence's page version check still governs the final write; comment changes made on another host during the final request can race because comment creation does not expose an atomic page-version condition.
