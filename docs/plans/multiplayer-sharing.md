# Multiplayer sharing: identity, ownership, share lists, guests, and the Lab

**Status:** Phase 0, the host-and-cloud half of Phase 1, the share dialog and badges, and the guest link route implemented (2026-09-15). The full plan is the work "Solus Multiplayer — Sharing, Comments, Artifacts, and the Fleet Lab"; this file records the vocabulary and the decisions the code now depends on, with the section numbers the code comments cite.

## Vocabulary

- **organization** — a Better Auth organization. Owns hosts. Members have role `owner` or `member`.
- **team** — a Better Auth nested team inside one organization.
- **guest** — a person with a share link and no account. Identified by a random stable `guestId` the browser keeps; may type a display name.
- **resource** — a session, a work, or a task. `ShareResource` is `{ kind: 'session' | 'work' | 'task', id }`. A task's share reaches everything in it: its page, the sessions attempted under it, and the works linked to it.
- **owner** — the person who started the session or created the work. Recorded on the host; exactly one per resource.
- **host owner** — the personal host's owner. Every role on every resource, because they own the disk. A managed host has none.
- **host admin** — who administers the machine: the host owner, or an organization owner on a managed host.
- **share list** — the rows that give a user, a team, the organization, or everyone-with-the-link a `viewer` or `editor` role on one resource.

## §3.2 Grant claims

A host grant (`packages/contracts/src/uplink.ts`, `hostGrantClaimsSchema`) carries, beside the Uplink fields, `access` (`owner | org-member | guest`), `hostKind` (`personal | managed`), `organizationId`, `organizationRole`, `teamIds` (at most 32), `hostOwnerUserId`, `displayName`, and `picture`. `sub` is `user:<id>` or `guest:<id>`. The host authorizes with ids only; the cloud never learns what a resource is.

The host parses claims with the contract schema. A narrower schema strips the membership facts and admits every member as the owner; that was the first defect the Lab found.

## §3.3 Principals

`packages/server/src/server/principal.ts`: `local-owner`, `remote-owner`, `org-member`, `guest`, `system`. A guest socket is bound to one resource, one role, the sharer's user id, and the hash of the link secret it arrived with; every call re-checks that the `everyone` row still holds that hash, so a regenerated link ends the visit. `isHostAdmin` is true for the host owner and for an organization owner on a managed host, nothing else.

## §3.4 Ownership and share lists

`packages/server/src/sharing/share-manager.ts` owns two tables and nothing else joins them: `resource_owner (organization_id, kind, id, owner_user_id)` and `share_grant (organization_id, kind, id, subject_kind, subject_id, role, link_secret_hash, granted_by_user_id)`, declared in `sharing/schema.ts` for both engines (docs/plans/cloud-service-model.md). Ownership lives in its own table rather than on the `sessions` and `works` rows because the transcript indexer rewrites session rows. Every manager method is asynchronous and scopes its rows by the organization the caller's principal names (`organizationOf`); `roleFor`, the access policy, the event audience, and every list filter await it.

Rules the code enforces:

- The first principal to name a new session (`watchSession`, `bindRuntimeSession`, `prompt`, `createHeadlessSession`) or to create a work owns it. A resource made over a local connection records the sentinel owner `host-owner`, which a remote owner also is.
- **A share is people plus a scope (decision 2026-09-17, refining the scope-only model of 2026-09-16).** A member holds what the rows give them: their own row, a team they are in, or the organization, the highest of them. The dialog has two sections: the people invited by name, each with a role of their own, and one general-access choice — only the owner, a team, the organization, or anyone with the link — with one role for that choice. Scopes nest (the organization holds every team; the link keeps the organization row), so widening never takes the resource from a narrower group, and a person's own row survives any scope change. A resource made on a managed host starts with an organization row as editors (the machine is the team's); one made on a personal host starts private. The host's own unowned work on a managed host (automations) is the team's to edit. Listings show a member what they own, what a row names them on, and that unowned work. Only the owner transfers or deletes.
- **A task's share reaches what is in it (2026-09-17).** A task is a resource like a session or a work: whoever creates it (`tasksCreate`, `tasksPrepareForSession`) owns it. `roleFor` on a session or work is the highest of its own standing and the standing on every task it is linked to, short of ownership (a task's owner edits the sessions in it but never owns one started by someone else). Listings of sessions and works include what a visible task holds; task listings (`tasksList`, `tasksSidebarSnapshot`) are filtered to what the caller may open. The tasks domain answers the two questions the share manager asks (`packages/server/src/tasks/task-sharing.ts`): what a task contains, and which tasks contain a resource; the share manager joins none of the task tables itself. A session's or work's share list names the tasks it is shared through (`inheritedFrom`). The share tables' CHECK constraints predate task sharing on older hosts, so the manager rebuilds them once, rows and indexes kept.
- A guest is bound to the one resource its link names; a resource with no `everyone` row admits no guest. A guest bound to a task reaches the task page, the sessions and works in it, and the filtered task listing, at the link's role; nothing else.
- The link is one `everyone` row. The host keeps the secret beside its SHA-256 hash (the hash is what admission and a guest's binding compare), and answers it in the share list to the owner and editors, so the link is always at hand to copy; a viewer sees only that a link exists. Regenerating or removing it disconnects every guest on the resource within the second; changing its role keeps them connected with the new role.
- Removing a member keeps their socket; their next call on the resource is `FORBIDDEN`, and they receive one `share.changed` event naming who removed them.
- Session ids are canonicalized through the lineage table, so a share made on the stable id also covers the provider thread id.

## §3.7 Access policy

`packages/server/src/server/access-policy.ts` classifies every RPC method: `local-only`, `host-admin`, `host-wide`, or `resource` with a locator for the session, work, or task id and the least role the call needs. Task reads (`tasksGet`, `tasksSessions`, `tasksSnapshot`) take a viewer, changes (`tasksUpdate`, comments, links) an editor, `tasksDelete` the owner. `assertRpcAccess` runs on every dispatch; a guest passes only resource calls on what its link reaches, a handful of boot calls, and the two task listings, which the handler filters. List RPCs (`listSessions`, `searchSessions`, `listWorks`, `tasksList`, `tasksSidebarSnapshot`) filter to what the caller may open, and the host event stream is filtered per connected principal (`packages/server/src/sharing/event-audience.ts`; a task guest also hears `tasks.invalidated`).

## Cloud

`solus-cloud`: `host.kind` and `host.organization_id`; `POST /v1/hosts/:id/grant` mints owner grants for the owner and member grants for members of the host's organization (a host outside both is "not found"); `POST /v1/hosts/:id/guest-grant` needs no session, is rate-limited per address and host, and proves only a name; `PUT /v1/hosts/:id/organization` shares or takes back a host; `GET /v1/orgs/:id/directory` lists members and teams for the share dialog; `GET /v1/hosts` includes hosts shared with the caller's organizations. Anyone may found an organization.

## The proxied-listener rule on sockets

The transport released the engine request on the engine's `connection` event, before Socket.IO builds the handshake, so `handshake.headers` was empty and the tunnel marker was never read: every socket through the tunnel listener looked like a loopback one. The request is now released after the handshake is built. `tests/unit/tunnel-socket-admission.test.ts` and the Lab's `uplink-admission` scenario hold the rule.

## §4 Sharing in the clients

One `ShareDialog` (`packages/workspace-ui/src/components/sharing/`) for sessions, works, and tasks, mounted once per shell (desktop `App.svelte`, web `App.svelte`) and opened through `sharesStore.open(target)`. A modal where there is a keyboard; a bottom sheet on a phone. Entry points: a `ShareButton` on the work header, the session band, and the task page's chrome bar (the phone's record bar carries "Share…" in its menu), a "Share" row in the phone's task sheet, the work header's overflow menu, the session context menu, the presence roster's "Who can open…" row, the command palette, and `⌥⇧.` (`global.share`) on the active session. Every entry point hides unless the resource's host is linked to Solus cloud (`sharesStore.canShareFrom(serverId)`, read from the host's `uplinkStatus` with the saved directory row as fallback): an unlinked host can mint no guest grant and names no organization, so a share made there reaches nobody. The gate is the host's link, not the client's sign-in — the web and mobile clients hold no account state of their own, and a signed-out desktop on a linked host can still copy a working link. The desktop palette keeps its "Share…" command and says why it cannot run instead.

The dialog reads the share list from the host (`shareGet`) through `sharesStore`, which re-reads on `share.changed` (a task's change also re-reads the cached session and work lists on that host) and shows "Access removed by <name>" when the change names this client. It has two sections, as a document's does. **People with access**: the owner, then everyone invited by name, each with a **Can view / Can edit / Remove access** menu, and an "Add people" search over the organization's directory (`personRows`, `personCandidates`, `withPersonRole`, `withoutPerson` in `lib/share-rows.ts`). **General access**: one dropdown — only the owner, each team of the organization, the organization, anyone with the link (`scopeOptions`) — with one **Can view / Can edit** menu beside it; the list's scope is the link if there is one, else the widest group row, with that row's role (`scopeOf`). Choosing a scope, or a role on it, sends the rows it stands for with the people kept as they are (`grantsFor`) and turns the link on, off, or to the new role in one store command (`sharesStore.setScope`); a role change on the link keeps its secret. The link scope keeps the organization row as it was so a teammate finds the resource in their sidebar rather than at the guest door. A group that is off starts as editors and the link as viewers. A session or work shared through a task says so under the people ("Also open to whoever can open the task …"). The session band's presence stack opens the room's roster with a Follow action per person and a "Who can open…" row into this dialog. Teams, people, and the organization's name come from the directory (`GET /v1/orgs/:id/directory`), fetched through the account source: the cookie on the cloud-served web client, the Electron main process on desktop (`uplinkOrganizationDirectory`). The host names this client's organization in `connectionsGetServerInfo` (`userId`, `organizationId`). Copy link is always in the footer: with no link yet it widens the scope to the link first, then copies, as a full guest link when the host is linked to Solus cloud and as the bare secret otherwise. The badge says the scope and the number of people named. `shareTransfer` stays on the host but the dialog no longer offers it.

## §4.2 The guest link

A link is `<account origin>/app/#/h/<hostId>/s/<secret>`. The secret rides the fragment, so the account origin never sees it; only a host can turn it into anything. The web client served at `/app/` recognizes the fragment before any catalog boot (`apps/client/src/main.ts`) and lands the visitor on `GuestLanding.svelte`: one question, the name other people see, kept with a random stable `guestId` under `solus.guest` in the browser. Nothing is written to the host registry, and the fragment stays in the address bar so a reload walks the same door.

The dial is the Uplink dial with two differences (`packages/client-core/guest-link.ts`, `server-connection.ts` `guest` option): the grant comes from `POST /v1/hosts/:id/guest-grant` with no session, and its answer names the host's tunnel route because a guest has no directory; and every `/auth/ws-ticket` exchange carries `{ shareSecret }`. A fresh grant the host refuses means the link was turned off or regenerated: the transport blocks, and the shell shows "This link no longer works".

The host tells the guest what it was let in to see: `connectionsGetServerInfo` answers `share: { resource, role }` and `displayName` for a guest principal. `GuestApp.svelte` builds the same app core as the workspace and opens exactly that resource, on that host: a work through the work route and `WorkPane`, a task through the task route and `TaskPage` (its sessions open in the same shell, with the task as the crumb before the session in the guest band, which is the way back), a session through `readSessionMeta` and `resumeSession` and `ConversationView`. Beside the pane, where the window is wide enough, is the guest rail (`apps/client/src/shell/GuestRail.svelte`): what was shared and the standing the guest holds on it, the sessions under a shared task (each a way in), and who is in the session on screen. Every row is a fact the host already sent; the rail asks for nothing host-wide. A control in the band hides it, and a phone never shows it — the band's crumb and the task page's own sessions list reach the same places. It mounts no sidebar, project panel, palette, settings, or catalog boot; the host would refuse those calls, and `rpc_access_refused` in the host log is how a guest shell is audited for host-wide reach. Opening a session by id needs `describeSession`, `resolveSessionLineage`, and `getSessionInfos` with one id, which are therefore resource-classed on the session they name (§3.7). The task page reads `tasksSidebarSnapshot`, which the handler filters to the guest's one task.

A viewer's document is read-only in the editor (`DocumentModal` reads the caller's role from the share list). A session is the workspace's own conversation column: the transcript with the composer (`EditorInputCard`) floating over its bottom edge and the column holding its band (`ComposerDock`, the same measurement `WorkspaceBody` makes for the workspace dock). The composer is always there. An editor's is live, with a line saying whose account the turn runs on; a viewer's takes no input, shows "You can view this session but not send prompts." in place of a prompt, and its toolbar is inert (`readOnlyReason` on `EditorInputCard` and `InputBar`, `readOnly` on `InputToolbar`; the session's own read-only state, a worktree that is gone, still applies without it). The host runs a guest's turn on the seat of whoever made the link (`seatUserFor` in `packages/server/src/seats/seat-manager.ts`: `sharedByUserId` is the `granted_by_user_id` of the `everyone` row; a link made over a local connection runs on the host login). Permission escalation to the sharer is still to come.

## §8 The Lab

`packages/lab` — see its README. `bun lab run all` runs the scripted proofs against a personal and a managed host; `scripts/lab-cloud-proof.ts` runs a host against a live cloud dev server; `scripts/lab-guest-proof.ts` opens real share links in a headless browser against a Lab host, with a miniature account origin minting the guest grants.
